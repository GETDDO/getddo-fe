# CONTEXT.md — 도메인 맥락

코드를 만지기 전에 읽는 도메인 용어·코드 매핑과 FE 고유 판단 기준이다.
"어떻게 쓰는가"(코드 규칙)는 [AGENTS.md](../AGENTS.md)가 담당하고, 여기는 "도메인이 코드의 어디에 있으며 무엇을 조심하는가"만 담는다.

**도메인 정책의 기준 문서는 공용 명세 저장소 `../getddo-spec/`다.** 이 파일의 도메인 서술이 spec과 다르면 spec을 따르고, 미확정 정책은 `../getddo-spec/00-requirements/pending-decisions.md`를 확인한다. 기획 맥락(페르소나·유저플로우·비기능)은 [product-context.md](product-context.md)를 읽는다.

## 서비스 핵심 원칙

**"검증 가능한 공정한 추첨"**이 이 서비스의 존재 이유다. 추첨 시점의 명단·응모권 수·가중치·조건을 스냅샷으로 보존하고 시드·입력 순서를 남겨 관리자가 결과를 재현·검증한다. 응모권 이력은 수정·삭제 없이 누적하며 이력 합계와 잔액이 항상 일치해야 한다. UI를 만들 때 "이 화면이 불투명해 보이지 않는가"를 기준으로 삼는다.

## 도메인 모델 → 코드 매핑

용어 정의의 원본은 `../getddo-spec/02-domain/glossary.md`다. 아래는 용어가 코드의 어느 슬라이스에 있는지의 매핑이다.

| 용어           | 코드                                        | 메모                                                                                                         |
| -------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| 이벤트         | `Event` (`entities/event`)                  | 응모권 미사용 / 사용(가중치 적용·미적용) 유형                                                                |
| 응모           | `Entry` (`entities/entry`)                  | 이벤트 추첨 신청. 출석·미션·게임은 응모가 아닌 별개 행위다                                                   |
| 응모 접수 완료 | —                                           | 서버가 유효하게 접수한 응모. 관리자의 '참여 허용' 판단과 구분한다                                            |
| 응모권         | `Ticket` (`entities/ticket`)                | **공통 재화** — 특정 이벤트에 종속되지 않는다. KST 기준월 만료, 이력은 수정·삭제 없이 누적                   |
| 응모권 내역    | ticket history                              | 지급·차감·반환·만료·회수를 별도 이력으로 기록. 이력 합계와 잔액이 항상 일치해야 한다                         |
| 추첨·발표      | `DrawResult` (`entities/draw-result`)       | 유형 무관하게 마감 + 5분 검토 후 **자동** 최초 발표 (`getddo-spec` ADR-009). 수동 최초 추첨·발표 승인은 없다 |
| 재추첨         | redraw (`features/run-redraw`)              | 당첨 취소 건에 한해 관리자 수동 실행. 최초 추첨과 연결 관계를 보존하고 덮어쓰지 않는다                       |
| 당첨자         | `Winner` (`entities/winner`)                | `userId`, `rank`, `prizeName`. 발표 시 마스킹한 이름·전화번호·이메일로 표시                                  |
| 출석           | attendance (`features/check-attendance`)    | 사용자 단위 일일 체크. 초기 1일 1장 지급, **매일 00:00 KST 초기화**                                          |
| 미션           | `Mission` (`entities/mission`)              | 서비스 공통 퀴즈·설문. 사용자당 미션별 1회 달성·보상. 연속 출석은 미션이 아닌 출석 도메인, 주간 미션은 보류  |
| 게임           | `Game` (`entities/game`)                    | 횟수 제한 없이 플레이 가능하나 보상은 사용자별·게임별 하루 1회 1장. 점수는 서버가 판정                       |
| 어뷰징 검토    | abuse review (`features/review-abuse-case`) | 탐지→관리자 검토(참여 허용/추첨 대상 제외). 탐지만으로 자동 제외하지 않는다                                  |
| 응모권 회수    | revoke (`features/revoke-ticket`)           | 부정 획득분 회수만 허용. 임의 지급·잔액 수정 기능은 없다                                                     |
| 알림           | `Notification` (`entities/notification`)    | 사이트 내 알림함. 실제 문자·이메일·푸시는 제외(모의 발송)                                                    |
| 가상 사용자    | session (`entities/user/model/session.ts`)  | 시연용 고정 ID 사용자. 로그인 화면에서 사용자/관리자 역할을 선택해 진입한다                                  |

## 이벤트 상태 전이

상태 목록과 전이 조건의 원본은 `../getddo-spec/02-domain/event.md`다 (`진행 예정 → 진행 중 → 마감 → 추첨 결과 확정·발표 대기 → 결과 발표 완료`, 별도 상태로 `중단`, `취소`, `재추첨`).

현재 `entities/event/model/types.ts`의 `upcoming → open → closed → drawn`은 목업용 단순화다. 실서버 연동 시 spec 상태 체계로 확장해야 하므로, 현재 enum에 의존한 로직을 넓게 퍼뜨리지 않는다.

## 시간 규칙 — 반드시 지킬 것

정책 원본은 `../getddo-spec/00-requirements/functional-requirements.md`의 "공통 시간 기준과 화면 표시"다.

- 서버와 주고받는 시각은 **UTC ISO 8601** 문자열(또는 오프셋 명시), 화면 표시는 `shared/lib/date`의 `formatKst`만 사용한다
- **업무 기준일·기준월은 KST다** — 일일 출석·게임 보상은 매일 00:00 KST에, 연속 출석·응모권 귀속월·만료는 매월 1일 00:00 KST 경계를 따른다. 관리자가 화면에 입력하는 운영 시각도 KST로 해석한다
- **마감·발표 판정은 서버 시각 기준**이다. 마감 전 접수 완료된 응모는 응답이 늦게 도착해도 유효하고, 클라이언트 시각으로 마감 여부를 판정해 버튼을 막는 로직을 만들지 않는다 (표시용 카운트다운은 허용)
- 마감 후 발표 카운트다운도 **서버가 제공한 발표 예정 시각** 기준으로 계산한다 — 새로고침·재접속으로 5분이 리셋되지 않아야 하고, 타이머 종료만으로 미공개 결과를 노출하지 않는다
- 시간 판정이 필요한 로직은 `new Date()`를 직접 호출하지 않고 `useVirtualClock().now()`(`app/virtual-clock`)를 경유한다 — 관리자 시간 여행(시연)이 오버라이드할 수 있어야 하기 때문이다

## 중복 방지·멱등키

"같은 요청의 재시도와 새로운 요청을 구분한다"는 확정 정책이다 (`../getddo-spec/02-domain/entry.md` — 응모권 미사용 이벤트도 동일).

- 재시도·중복 클릭으로 같은 부작용이 두 번 생기면 안 되는 POST에는 `shared/lib/idempotency-key`의 `createIdempotencyKey()`로 생성한 키를 헤더에 붙인다
- 현재 대상: `POST /events/:eventId/entries`(응모). 추첨·재추첨·회수 등 새 부수효과 요청에도 같은 판단을 적용한다
- 헤더명·생성 주체·전달 방식은 FE-BE 미합의 — 임시로 `X-Idempotency-Key`를 쓰고, 합의 시 공통 상수로 승격한다

## 비공개·마스킹 — FE 고유 책임

정책 원본은 `../getddo-spec/02-domain/drawing.md`(결과 발표)다. FE가 특히 지켜야 할 것:

- **발표 전 당첨 결과는 비공개**다. 재접속·직접 조회로도 노출되면 안 되므로, 발표 상태 확인 없이 결과를 렌더링하는 코드를 만들지 않는다
- 발표 결과는 **마스킹한 이름·전화번호·이메일**로 표시한다 — 공개 화면과 응답 데이터 모두에 적용 (마스킹 세부 규칙은 담당자 미정)
- **당첨 확률은 표시하지 않는다** — 실시간 현황에 표시하는 것은 응모자 수(중복 제거), 응모 건수, 총 차감 응모권 수, 본인 차감 응모권 수까지다
- 어뷰징 제외는 **본인에게만** 사유를 안내하고 일반 낙첨과 구분된 문구를 쓴다. 다른 사용자의 탐지 수치·정보는 비공개
- 재추첨 진행 과정·연출은 관리자 화면에만 제공한다

## 사용자 역할·시연

`UserRole = 'user' | 'admin'` (`entities/user/model/session.ts`).

- 로그인 화면의 역할 선택은 **데모 전용**이다. 관리자 권한은 역할 선택만으로 부여되지 않고 서버의 별도 인증을 거친다 (비기능 요구사항 '시연 로그인 및 관리자 보호' — product-context.md)
- 사용자 역할은 서버가 결정하며, 클라이언트가 보낸 role 값을 신뢰하지 않는다 — 권한 우회용 role 변경 코드를 만들지 않는다
- MSW 개발 환경에서 세션이 `admin`으로 시작하는 것은 목업상 관리자 화면 확인을 위한 편의 장치다
- 관리자는 응모할 수 없다 (임직원 여부는 응모 제한 조건으로 사용하지 않는다 — `getddo-spec` 기능 요구사항)

## 백엔드 연동 전 임시 상태

합의되지 않은 항목은 임의로 확정해 하드코딩하지 않는다. 미결정 전체 목록은 `../getddo-spec/00-requirements/pending-decisions.md`가 기준이다.

- 멱등키 생성 주체·전달 방식 — 미합의
- 에러 코드 체계·페이지네이션 형식 — 미합의 (`shared/api/client.ts` 인터셉터에 확정 시 매핑 추가)
- 가중치 환산 계산식·가중치 값의 상한·추가 배율 — 보류 (응모권 **사용 수량** 상한은 누적 5장으로 확정됨. 둘을 혼동하지 않는다)
- 당첨자 마스킹 세부 규칙 — 담당자 결정 대기
- 마감 + 5분 자동 발표가 장애·정합성 오류로 실패했을 때의 사용자 문구·복구·취소 기준 — 미확정
- 배너 이미지 형식·용량 제한 — 담당자 확정 대기

MSW 목업(`shared/api/mocks/handlers/`)은 계약의 임시 구현이다. Zod 스키마(`entities/*/model/`)가 검증 기준이며, 도메인 정책의 원본은 `../getddo-spec/02-domain/`에 있다.
