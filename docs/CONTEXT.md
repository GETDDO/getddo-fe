# CONTEXT.md — 도메인 맥락

코드를 만지기 전에 읽는 도메인 용어·코드 매핑과 FE 고유 판단 기준이다.
"어떻게 쓰는가"(코드 규칙)는 [AGENTS.md](../AGENTS.md)가 담당하고, 여기는 "도메인이 코드의 어디에 있으며 무엇을 조심하는가"만 담는다.

**도메인 정책의 기준 문서는 공용 명세 저장소 `../getddo-spec/`다.** 이 파일의 도메인 서술이 spec과 다르면 spec을 따르고, 미확정 정책은 `../getddo-spec/00-requirements/pending-decisions.md`를 확인한다. 기획 맥락(페르소나·유저플로우·비기능)은 [product-context.md](product-context.md)를 읽는다.

## 서비스 핵심 원칙

**"검증 가능한 공정한 추첨"**이 이 서비스의 존재 이유다. 추첨 시점의 명단·응모권 수·가중치·조건을 스냅샷으로 보존하고 시드·입력 순서를 남겨 관리자가 결과를 재현·검증한다. 응모권 이력은 수정·삭제 없이 누적하며 이력 합계와 잔액이 항상 일치해야 한다. UI를 만들 때 "이 화면이 불투명해 보이지 않는가"를 기준으로 삼는다.

## 이벤트 상태 전이

상태 목록과 전이 조건의 원본은 `../getddo-spec/02-domain/event.md`다 (`진행 예정 → 진행 중 → 마감 → 추첨 결과 확정·발표 대기 → 결과 발표 완료`, 별도 상태로 `취소`, `재추첨`). 이벤트 일시 중단·재개는 2026-10-06 `getddo-spec` ADR-015로 제외됐다 — 중단 상태·중단 시각·중단/재개 조작을 새로 만들지 않는다. 어뷰징 전원 제외로 끝나는 '추첨 대상자 없음'(`NO_ELIGIBLE_ENTRANTS`) 종료 상태도 2026-10-11 ADR-018로 신규 사용이 폐지됐다 — 과거 이력의 조회 호환성만 담당자가 별도 검토한다.

현재 `entities/event/model/types.ts`의 `upcoming → open → closed → drawn`은 목업용 단순화다. 실서버 연동 시 spec 상태 체계로 확장해야 하므로, 현재 enum에 의존한 로직을 넓게 퍼뜨리지 않는다.

이벤트 수정·등록 제한 (관리자 폼 구현 시 반영, 원본 `02-domain/event.md`):

- 이벤트 등록과 경품·당첨 인원 등록은 함께 성공하거나 함께 실패한다 — 경품 없이 이벤트만 등록되지 않는다. 같은 등수에는 한 종류의 경품만 등록한다
- 시작 전이며 진행 예정 상태에서만 수정 가능하다. 취소 상태는 시작 전이라도 수정 불가이고, 시작 시각은 앞당길 수 없다(늦추기만 가능). 진행 중·마감 후에는 수정 불가
- 시작 전이며 응모 이력이 없는 이벤트만 삭제할 수 있다. 삭제해도 연결 배너는 자동 삭제되지 않고 관리자가 배너 관리에서 수동 삭제한다 — 삭제·취소 이벤트에 연결된 배너는 사용자 목록에서만 숨긴다(ADR-021·ADR-023)

## 실시간 응모 현황 갱신

요구사항 원본은 기능 요구사항 7절이다. 갱신 주기와 방식은 구현 담당자 재량으로 위임됐고 `05-api/entry.md`는 E03 재조회 제안과 함께 SSE·WebSocket을 필수로 두지 않는다고 명시한다.

- 현황 수치는 **E03 전용 조회** `useEntryStatistics(eventId)`(`entities/entry`)로 받는다 (ADR-0007). 진행 중(`open`) 이벤트만 **30초 폴링**하고, 그 외 상태는 폴링하지 않는다. 홈 배너처럼 여러 이벤트가 겹치는 곳은 현재 보이는 항목만 켠다
- `useEventList`·`useEvent`의 폴링은 현황이 아니라 **상태 전환 감지** 용도다 — 상세는 추첨 완료(`drawn`)까지 폴링한다 (마감 상태는 결과 발표 전환을 감지해야 한다)
- **응모 성공 직후 즉시 재조회**는 `useEnterEvent`의 `onSuccess` 무효화(`['events']`·`['tickets']`·`['entries']`)가 담당한다. E03은 `['entries', 'statistics', eventId]`라 함께 무효화된다
- 표시 지표는 E03의 `participantCount`(접수 완료 응모자의 중복 제거 수)·`totalSpentTicketCount`(그 응모자들의 누적 차감 합계, 반환은 빼지 않음)·`mySpentTicketCount`(본인 누적 차감, 미응모·관리자는 0)다 — 2026-10-14 GD-200으로 현행 구현 기준 확정됐고 거절 이력은 포함하지 않는다. `Event`에는 응모 현황 필드가 없다 (`myEntryCount`는 본인 응모 건수 표시용으로 남아 있다). 당첨 확률은 표시하지 않는다

## 시간 규칙 — 반드시 지킬 것

정책 원본은 `../getddo-spec/00-requirements/functional-requirements.md`의 "공통 시간 기준과 화면 표시"다.

- 서버와 주고받는 시각은 **UTC ISO 8601** 문자열(또는 오프셋 명시), 화면 표시는 `shared/utils/date`의 `formatKst`만 사용한다
- **업무 기준일·기준월은 KST다** — 일일 출석·게임 보상은 매일 00:00 KST에, 연속 출석·응모권 귀속월·만료는 매월 1일 00:00 KST 경계를 따른다. 관리자가 화면에 입력하는 운영 시각도 KST로 해석한다
- **마감·발표 판정은 서버 시각 기준**이다. 마감 전 접수 완료된 응모는 응답이 늦게 도착해도 유효하고, 클라이언트 시각으로 마감 여부를 판정해 버튼을 막는 로직을 만들지 않는다 (표시용 카운트다운은 허용). 서버의 마감 판정은 응모 트랜잭션 커밋 직전의 최종 확인이며, 그 확인과 커밋 확정 사이의 미세 간격 안에 커밋된 응모는 마감 전 접수로 인정한다(GD-205)
- 마감 후 사용자 화면은 **'응모 마감 · 결과 발표 대기'만 표시**한다 — 5분 카운트다운과 고정 발표 예정 시각은 없다(ADR-022). `publicationScheduledAt`은 E08·E09와 이벤트 목록·상세 응답에서 제외됐고, 관리자 응답에만 최초 자동 추첨 기준 시각 `drawScheduledAt`(`endsAt`+5분)이 있다(GD-203)
- 최초 공개는 **관리자 수동 공개 요청**이다 — 결과 확정·관리자 확인 저장·시간 경과만으로 공개되지 않고, 스케줄러의 자동 공개·공개 재호출도 없다. 확인(`POST /admin/draws/{runId}/result-confirmation`)과 공개는 별도 동작이며 입출력·오류 세부는 GD-199 후속이다. 서버가 실제 공개하기 전 결과는 표시하지 않는다
- 시간 판정이 필요한 로직은 `new Date()`를 직접 호출하지 않고 `useVirtualClock().now()`(`shared/model/virtualClock`)를 경유한다 — 관리자 시간 여행(시연)이 오버라이드할 수 있어야 하기 때문이다. 순수 함수는 `now`를 인자로 받는다(`shared/utils/date` 참조)

## 중복 방지·멱등키

"같은 요청의 재시도와 새로운 요청을 구분한다"는 확정 정책이다 (`../getddo-spec/02-domain/entry.md` — 응모권 미사용 이벤트도 동일).

- 재시도·중복 클릭으로 같은 부작용이 두 번 생기면 안 되는 POST에는 `shared/utils/idempotencyKey`의 `createIdempotencyKey()`로 생성한 키를 `IDEMPOTENCY_HEADER` 헤더(`Idempotency-Key`)에 붙인다
- 작업별 구분은 `05-api/common.md` 초안을 따른다: 응모·미션=멱등키(응모의 키는 UUID이며 응모 요청 결과(접수 또는 저장된 거절)의 ID로 그대로 쓴다 — GD-134·GD-145), **출석=사용자·KST 기준일 재처리**, **게임=서버 발급 `playId`**, 알림 읽음=사용자·알림 ID. 추첨·재추첨 등 새 부수효과 요청에도 같은 판단을 적용한다
- 같은 키·다른 본문의 재요청은 409로 거절하고, 같은 키·같은 본문은 처음 결과를 200으로 돌려준다 (목업 `entry.ts`도 동일하게 동작)

## 비공개·마스킹 — FE 고유 책임

정책 원본은 `../getddo-spec/02-domain/drawing.md`(결과 발표)다. FE가 특히 지켜야 할 것:

- **발표 전 당첨 결과는 비공개**다. 재접속·직접 조회로도 노출되면 안 되므로, 발표 상태 확인 없이 결과를 렌더링하는 코드를 만들지 않는다
- 발표 결과는 **마스킹한 이름과 전화번호 끝 4자리**로 표시한다 — 이름은 외자면 성만, 그 외는 처음과 마지막 글자만 드러낸다(예: 김수→김*, 김민수→김*수, 남궁민수→남**수). 이메일은 화면·응답 모두에 포함하지 않는다. 미등록 값의 대체 표시는 이번 범위 제외 (2026-10-14 확정, `02-domain/drawing.md` 결과 발표)
- **당첨 확률은 표시하지 않는다** — 실시간 현황에 표시하는 것은 응모자 수(중복 제거), 응모 건수, 총 차감 응모권 수, 본인 차감 응모권 수까지다
- 등급 응모권(ADR-014)에서는 **실제 장수와 추첨 가중치를 구분해 표시**한다 — 골드 1장은 장수 1·가중치 5다. 등급 획득 확률(80/18/2%)을 이벤트 당첨 확률처럼 표시하지 않는다. 등급별 보유량 표시용 공개 API 필드는 담당자 검토 후 확정이므로 임의로 만들지 않는다
- 신규 추첨 제외와 제외 사유 안내는 제공하지 않는다(ADR-018) — 본인 결과의 `EXCLUDED`와 '추첨 대상자 없음' 종료 표시를 새로 만들지 않는다. 다른 사용자의 탐지 수치·차단 기록·검증 근거는 비공개
- **관리자 미확인 재추첨 결과는 공개 명단·본인 결과·알림 어디에도 노출하지 않는다** — 최초 공개 전이든 발표 후든 동일하다. 결과 확정·확인 저장만으로 공개되지 않고 명시적 관리자 공개 요청이 필요하다(ADR-022)
- 발표 후 명단 갱신 안내는 **당첨 취소자와 새 당첨자에게만** 생성된다 — 전체 응모자에게 재발표 알림을 보내지 않는다
- 발표 후 취소~공개 갱신 사이의 취소자 임시 표시·본인 중간 결과는, 이번 운영에서 발표 후 취소·재추첨을 사용하지 않는 전제로 GD-140 범위에서 제외다 — 관리자 취소·재추첨 API는 유지되며 해당 운영을 시작하기 전 표시 계약을 보완한다
- 재추첨 진행 과정·연출은 관리자 화면에만 제공한다

## 사용자 역할·시연

`UserRole = 'USER' | 'ADMIN'` (`entities/user/model/types.ts`) — spec과 BE `UserRole` enum의 대문자 표기를 따른다.

- 로그인 화면의 역할 선택은 **데모 전용**이다. 관리자 권한은 역할 선택만으로 부여되지 않고 서버의 별도 인증을 거친다 (비기능 요구사항 '시연 로그인 및 관리자 보호' — product-context.md)
- 사용자 역할은 서버가 결정하며, 클라이언트가 보낸 role 값을 신뢰하지 않는다 — 권한 우회용 role 변경 코드를 만들지 않는다
- MSW 개발 환경에서 세션이 `ADMIN`으로 시작하는 것은 목업상 관리자 화면 확인을 위한 편의 장치다
- 관리자는 응모할 수 없다 (임직원 여부는 응모 제한 조건으로 사용하지 않는다 — `getddo-spec` 기능 요구사항)

- 사용자 문맥 헤더 — 결정(2026-10-12): `X-User-ID`·`X-User-Role`·`X-User-Membership`을 보내고, 백엔드는 헤더를 DB와 대조만 한다. 권한은 DB 역할로만 판단하며 헤더 역할로 권한을 올리지 않는다. 백엔드 `dev`의 `CurrentUserArgumentResolver`와 일치한다. 공용 근거는 [작업 기록](../../getddo-spec/04-worklogs/2026-10-12-user-context-header-decision.md)과 `common.md`. `src/app/config/sessionSync.ts`의 요청 인터셉터가 세션 사용자의 `X-User-Role`을 `X-User-ID`·`X-User-Membership`과 함께 모든 업무 API에 붙이고, 세션이 없으면 보내지 않는다 (GD-173)
- 당첨자 마스킹 — 2026-10-14 확정으로 해소: 이름은 외자면 성만·그 외 첫·끝 글자, 전화번호는 끝 4자리, 이메일은 공개하지 않는다 (`02-domain/drawing.md` 결과 발표). 미등록 값의 대체 표시는 이번 범위 제외
- 수동 최초 공개 후속(GD-199) — 최초 INITIAL 확인(`POST /admin/draws/{runId}/result-confirmation`, 본문 없음·활성 관리자)과 실제 공개 호출의 분리, 공개 요청의 입력·응답·오류·경로 확장 세부는 GD-199에서 보완한다. 발표 지연 안내·새 예정 시각 항목은 수동 공개 전환으로 소멸했고, 발표 후 취소~갱신 사이의 취소자 임시 표시·본인 중간 결과는 이번 운영 미사용 전제로 GD-140 범위 제외다. 남은 후속: 장애·정합성 오류의 복구·재시도·취소 전환 기준, 취소 요청의 `abuseCaseId` 선택 연계 방식(필수 조건 아님 — ADR-019), 전체 당첨 취소·전체 재추첨(추후 추가 예정)

- 추첨 관리 목업(GD-125) — `mocks/handlers/draw.ts`가 AD01~AD09 초안을 구현한다 — GD-169로 확정된 범위와 아직 검토 대기인 부분이 섞여 있다(`entities/drawResult`·`entities/winner`의 Zod가 검증 기준, 계약 테스트 `draw.test.ts`). 이벤트별 추첨 상태는 마감된 이벤트를 처음 조회할 때 후보 33명으로 만들고, 최초 추첨(자동)은 확정된 채 시작한다. 당첨 취소(AD05)는 재추첨 실행을 함께 등록하고, 재추첨은 실제 시계 기준 약 1.5초 PREPARING → 약 4.5초 이내 CONFIRMED로 진행한다(화면은 realtime 프리셋 30초 폴링 + 수동 새로고침). 시드: `adm-904`(재추첨 실패 → AD09 재개 시연), `adm-906`(최초 추첨 실패 → 최초 재개 시연), `adm-905`(최초 발표 전 — AD06 비활성 시연), `adm-902`(취소된 이벤트). 추첨 상태는 `adminEvent` 목업의 이벤트 상태(`REDRAWING` 등)와 연동하지 않는다. 최초 추첨을 수동으로 시작하는 API는 계약에 없어 화면에도 없다(마감+5분 자동 추첨). 목업의 자동 최초 공개 연출은 ADR-022로 폐지 대상이다 — 자동 추첨까지만 진행하고 사용자 화면은 '결과 발표 대기'를 유지하며, 관리자 확인·수동 공개(GD-199 세부 후속)로 재구성한다. AO03 지급 이력(`keyword` 이름 부분일치·대소문자 무시, `missionId`를 쓰면 MISSION만, `sourceType`·`grade` 필터, 지급 수는 `totalElements`), AO04 사용자별 정합성(응모권 `version`·`status`와 마지막 이력의 `version`·`status` 비교, 불일치 항목에 `ticketStatus`·`latestHistoryStatus` 포함, 없는 사용자 404 `TICKET-011`·활성 관리자 아님 403 `TICKET-010`), AO09 `GET /admin/tickets/inconsistencies`(전체 불일치 목록, 요청마다 계산), AO05 전체 이력(`userName`·`eventTitle`·`missionTitle` 추가), AO08 반환 이력(`status`·`attemptCount`·`completedAt`·`status` 필터 삭제, 행은 `ticketId`·`grade`·`eventTitle`·`userName`·`refundedAt`을 포함, `reasonType`은 `EVENT_CANCELED`만, 이벤트 취소→반환 연결 전까지 실서버는 빈 목록). 관리자 응모권 조회(AO03~AO09)는 읽기 전용이라 감사 기록 대상이 아니다. `entities/ticket`의 admin 스키마·훅·표, `mocks/handlers/adminTicket.ts`, `pages/admin/tickets`(`/admin/tickets`, 정합성·지급 이력·전체 이력·반환 이력 탭 + 사용자 정합성 서랍)가 이 계약을 따른다. 목업 AO08은 데모용 샘플 행이 있다
- 지급 전 차단 전환(ADR-018) 후속 확인 — 차단 적용 대상(게임만? 출석·미션 포함?), 명확한 규칙 위반과 의심을 구분하는 판정 기준, 지급 후 게임 점수 무효화·판단 근거 계약 변경 여부(개별 당첨 취소·재추첨은 ADR-019로 확정), 마감+5분 일정 유지 여부는 `pending-decisions.md`의 "지급 전 차단 전환의 후속 확인"을 따른다. 의심만으로 차단하는 새 기준을 임의로 도입하지 않는다
- 출석 DTO — AT01~AT03 계약을 맞췄다 (GD-151). `AttendanceToday`(attendanceDate·dailyRewardTicketCount·milestones·nextResetAt)와 `AttendanceReceipt`(`rewards[]`의 `rewardType` DAILY/STREAK·`milestoneDays`)는 entities/attendance 스키마가 기준이고, 주간 도트가 쓰던 `checkedDates`는 AT03 월별 조회(`attendanceDates`)로 대체했다. spec에 없는 임시 `GET /attendances/policy`는 제거하고 단계·일일 보상량은 AT01에서 읽는다. 출석 제출 429는 `COMMON-006`으로 사용자 분당 5회다(GD-146). 보상의 응모권 등급(브론즈) 공개 필드는 아직 DTO에 없다 — 담당자 검토 대기 (ADR-016, `pending-decisions.md`의 "등급 응모권")
- 어뷰징 목업·화면 — `mocks/handlers/abuse.ts`는 spec 요약 필드 대신 시연 표시 필드(userNickname·eventTitle·requestSummary)를 싣는다. 참여 허용·추첨 제외 결정 계약(AR03의 `ALLOW/CONFIRM`·`excludeFromEvent`·`userNoticeReason`과 `eligibilityStatus`, AO07의 제외 필터·필드)은 2026-10-11 ADR-018로 폐지됐다 — `features/reviewAbuseCase`의 결정 다이얼로그는 제거 대상이고, 화면은 차단 내역 조회(AR01~AR02: 차단 사유·발생 시각·관련 요청·검증 근거) 중심으로 재구성한다. 신규 차단 기록의 필터·필드 계약은 GD-141 설계에서 확인한다 (GD-102 잔여 + ADR-018)
- 관리자 알림 운영(AN01~AN05, 2026-10-12 확정) — 작업(`NotificationJob`)·알림(`AdminNotification`) 조회와 최종 실패 복구(AN03 생성·AN05 모의 발송)다. 자동 재시도는 최초 1회 + 최대 3회이고 입력·형식 오류는 즉시 최종 실패다. 복구는 202 접수(최종 성공이 아님)이며 정상 알림의 재생성·재발송은 없다. `retryable`이 false이거나 `generationStoppedBy`가 있으면 복구 버튼을 만들지 않는다. 사용자 알림 N01~N03 외 코드·목업은 아직 이 계약으로 전환하지 않았다
- `/virtual-users` — spec에 없는 시연 전용 경로로 로그인·가상 사용자 전환 UI가 쓴다. 봉투만 공통 계약을 따르고 정식 계약은 BE 협의 대상이다 (GD-102)
- 실연동 하이브리드(GD-213) — 모든 업무 API 경로가 `/api/v1/**`로 정합화됐고, 배포 빌드(`env.isDev=false`)는 `mocks/handlers/index.ts`의 `hybridHandlers`만 등록한다: 배포 BE에 없는 가상 사용자·배너·게임·감사·어뷰즈·관리자 응모권·사용자 결과 조회만 목업이고 나머지는 Vercel의 `/api/* → CloudFront` 프록시로 실서버에 붙는다(서버 목록은 배포 OpenAPI 기준). BE가 해당 도메인을 배포하면 `hybridHandlers`에서 빼는 것이 전환 절차다. `/virtual-users` 목업이 돌려주는 사용자 목록은 `VITE_VIRTUAL_USERS_JSON`으로 주입하며 id는 DB 등록 UUID여야 한다
- `index` 번들 ~618kB — 관리자 라우트는 페이지별 lazy로 분리돼 있고 사용자 번들은 vendor가 대부분이다. `manualChunks` 벤더 분리는 빌드 설정 변경이라 별도 이슈로 미뤘다 (GD-102 잔여)

MSW 목업(`src/mocks/handlers/`)은 계약의 임시 구현이다. Zod 스키마(`entities/*/model/`)가 검증 기준이며, 도메인 정책의 원본은 `../getddo-spec/02-domain/`에 있다.
