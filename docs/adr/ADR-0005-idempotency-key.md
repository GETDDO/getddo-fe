# ADR-0005: 중복 위험 요청에 멱등키 적용

- 상태: accepted
- 날짜: 2026-09-17

## 맥락

응모·추첨은 되돌리기 어려운 부작용을 만든다. 네트워크 재시도나 더블클릭으로 같은 요청이 두 번 가면 응모가 중복 생성되거나 응모권이 이중 차감될 수 있다. 클라이언트에서 버튼 비활성화만으로는 재시도를 막을 수 없다. 공용 명세도 "같은 요청의 재시도와 새로운 응모를 구분해 중복 반영을 방지한다"고 명시한다 (`../getddo-spec/02-domain/entry.md`) — 응모권 차감이 없는 미사용 이벤트 응모에도 적용된다.

## 결정

"재시도·중복 클릭으로 같은 부작용이 두 번 생기면 안 되는 POST"에는 `shared/lib/idempotency-key`의 `createIdempotencyKey()`로 생성한 키를 `IDEMPOTENCY_HEADER` 헤더에 붙인다.

- 현재 대상: `POST /events/:eventId/entries`(응모 — 사용·미사용 이벤트 모두)
- 헤더명은 spec 공통 계약 초안(`05-api/common.md`)의 `Idempotency-Key`를 따른다. 초안이라 확정 시 `IDEMPOTENCY_HEADER` 상수 값만 바뀌고 사용 지점은 그대로다 (2026-09-30 `X-Idempotency-Key`에서 교체)
- 작업별 구분은 spec 공통 계약 초안을 따른다:
    - 응모·미션 완료 등 중복 차감 위험 요청 → 멱등키
    - 출석 → 사용자·KST 기준일로 재처리되므로 멱등키를 쓰지 않는다. 같은 날 재요청은 서버가 200으로 기존 결과를 돌려준다
    - 게임 결과 → 서버가 발급한 `playId`로 재시도를 식별하는 초안이라 멱등키를 쓰지 않는다 (계약 미확정)
    - 알림 읽음 → 사용자·알림 ID 조합이 자연키라 멱등키를 쓰지 않는다
- 조회(GET)와 이미 멱등인 요청에는 붙이지 않는다

## 결과

- 새로운 부수효과 POST(추첨, 재추첨, 응모권 회수 등)를 추가할 때 멱등키 필요 여부를 먼저 판단한다
- MSW 핸들러가 멱등키 누락 시 400을 반환하므로, 목업 환경에서 누락을 바로 발견할 수 있다
- 출석 목업은 멱등키를 요구하지 않고, 같은 기준일 재요청은 확정한 결과를 200으로 재사용한다
