# ADR-0009: 목록 페이지네이션 UI 패턴

- 상태: proposed
- 날짜: 2026-10-08

## 맥락

spec 공통 계약(`../getddo-spec/05-api/common.md`)은 목록 응답을 `Page<T>`(1부터 시작하는 번호형)와 `Cursor<T>`(불투명 `nextCursor`) 두 가지로 제공한다. 어느 API가 어느 형식인지는 서버가 정한다. 반면 화면이 번호 이동을 보여줄지, "더보기"를 보여줄지는 FE가 정할 수 있다. 현재 코드는 다음처럼 섞여 있다.

- 관리자 감사 로그·이벤트 관리: `Page<T>` + `shared/ui/pager`
- 알림: `Cursor<T>` + `useInfiniteQuery`
- 응모권 이력: `Cursor<T>`
- 내 응모 내역·이벤트 목록: `Page<T>`를 전부 모아 한 번에 표시

## 결정

화면 유형으로 UI를 정하고, 응답 형식은 entities 쿼리 훅이 흡수한다.

| 화면 유형                                                  | UI                                 | 비고                                                                                                     |
| ---------------------------------------------------------- | ---------------------------------- | -------------------------------------------------------------------------------------------------------- |
| 관리자 테이블 (감사 로그, 어뷰징 검토, 이벤트·사용자 관리) | 번호형 `Pager`                     | 특정 페이지 이동·건수 확인이 필요하다                                                                    |
| 사용자 시간순 피드 (알림, 응모권 이력, 내 응모 내역)       | "더보기" 버튼 (`useInfiniteQuery`) | 모바일·큰글씨 모드에서 번호 버튼보다 조작이 쉽다. 자동 무한 스크롤은 쓰지 않는다 — 접근성·푸터 접근 문제 |
| 사용자 전체 표시 목록 (이벤트 목록 등 수가 적은 목록)      | 전부 모아 표시                     | 현재 방식 유지. 항목이 100건을 넘으면 "더보기"로 전환을 검토한다                                         |

- `Page<T>` API를 "더보기" 화면에 쓸 때는 `useInfiniteQuery`의 `getNextPageParam`에서 `page * size < totalElements`로 다음 페이지를 계산한다. 화면은 응답 형식을 모른다
- `Cursor<T>` API를 번호형으로 보여주지 않는다 — 커서는 임의 페이지 이동을 지원하지 않는다. 관리자 화면 API가 커서로 확정되면 그 화면만 "더보기"로 바꾼다
- 페이지 크기는 spec 기본값 20을 쓴다. 전부 모으는 목록만 요청 수를 줄이려고 50을 쓴다 (현행 유지)

## 결과

- 서버가 `Page`/`Cursor` 중 무엇을 고르든 화면 UI가 바뀌지 않는다 — 바뀌는 곳은 entities 쿼리 훅의 `getNextPageParam`뿐이다
- 후속 작업: 내 응모 내역(`useMyEntries`)을 "더보기" 방식으로 전환 검토 — 응모가 쌓이면 전부 모으는 방식의 요청 수가 늘어난다
